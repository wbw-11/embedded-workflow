# 外部变量与头文件组织：多文件工程结构

## R — 原文 (Reading)

> "在一个源程序的所有源文件中，一个外部变量只能在某个文件中定义一次，而其它文件可以通过extern声明来访问它。"（第4章 §4.5）
>
> "一个外部对象只能有一个定义"（第4章 §4.5/附录A）
>
> "我们尽可能把共享的部分集中在一起，这样就只需要一个副本，改进程序时也容易保证程序的正确性…这些公共部分放在头文件。"（第4章 §4.5）
>
> "某些对象不应该被其他函数访问，用static可以隐藏外部对象。"（第4章 §4.6）
>
> "在一个好的程序设计风格中，应该避免出现变量名隐藏外部作用域中相同名字的情况，否则，很可能引起混乱和错误。"（第4章 §4.2）
>
> — B. W. Kernighan & D. M. Ritchie, 第4章 §4.2-4.6

## I — 方法论骨架 (Interpretation)

多文件 C 工程的地基是"**单一定义 + 声明/定义分离**"：

- **定义 vs 声明**：定义分配存储（一个对象全工程只能有一个定义）；声明（`extern`/原型）不分配、告诉编译器类型与存在；
- **头文件放声明、源文件放定义**：把共享的接口（extern 声明、函数原型、类型、宏）集中进 `.h`，各 `.c` `#include` 同一个头——只维护一份副本，改一处全工程同步；
- **static 控制可见性**：不想让某外部对象/函数泄漏出本文件，就加 `static`（文件内链接）——这是"私有"机制；
- **反模式**：过度使用外部变量会让"数据关系模糊不清、值可能被意外或不经意地修改、程序修改困难"——优先用参数/返回值传数据，确需共享才用外部；
- **命名卫生**：避免内层/局部变量隐藏外部同名变量（遮蔽导致混乱错误）。

## A1 — 书中的应用 (Past Application)

### 案例 1: 逆波兰计算器拆成多文件
- **问题**: 单文件演变到多文件的工程组织——calc/main/getop/stack/getch 各部分怎么共享？
- **方法论的使用**: 公共类型与函数声明放一个头文件，各 .c 实现各自部分并 include 头；用 `static` 隐藏栈内部细节。
- **结论**: 头文件成为唯一接口契约，改进程序时保证正确性（只维护一个副本）。
- **结果**: 第4章多文件计算器成为"外部变量 + 头文件组织"的完整示范（第4章 §4.5-4.6）。

### 案例 2: 外部变量的反例（打印最长行第二版）
- **问题**: 作者给出用外部变量版本的打印最长行程序。
- **方法论的使用**: 他自陈该版本"数据关系模糊不清、变量值可能被意外修改、函数因用了全局变量名而不通用"。
- **结论**: 过度外部化是反模式，第一版（参数传递）"比第二个版本好"。
- **结果**: 该书用一正一反两个版本教会"外部变量要克制"（第1章 §1.10）。

### 案例 3: static 隐藏实现细节（fopen/getc 内部）
- **问题**: 不希望外部访问标准库内部状态。
- **方法论的使用**: 作者在实现标准库时用 static 限制内部变量/函数对本文件可见。
- **结论**: static = 文件私有，是封装工具。
- **结果**: 第7/8章的库实现示范（第8章 §8.4 等）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 项目从单文件长成多文件，出现"重复定义"或"undefined reference"链接错误；
2. 想在多个源文件间共享变量/函数，不确定声明放哪、定义放哪；
3. 想隐藏模块内部实现（static 私有函数/变量）或改造成库接口；
4. 重构一个全局变量满天飞的祖传代码，想清理数据流向；
5. 编写/审阅头文件时想定"哪些进 .h、哪些该加 static"。

## E — 可执行步骤 (Execution)

1. **盘点当前共享面**
   - 完成标准: 列出跨文件使用的变量、函数、类型、宏，标注各自当前声明/定义位置与可见性。
   - 判停条件: 发现某共享变量仅在一处使用，建议改局部化（消除不必要的外部）。

2. **🔴 CHECKPOINT · 仅局部化决策时确认**
   - 完成标准: 共享对象边界清晰、不需要动既有变量可见性时，直接进入步骤 3，不打断用户。
   - 判停条件: 仅当建议把某共享变量局部化/加 static 会改变其可见性（影响其他文件引用）时，向用户确认是否接受该改动，确认后再继续。

3. **划定 .h 与 .c 边界**
   - 完成标准: 每个共享对象：类型/宏/函数原型/需要 extern 的外部变量声明 → 一个公共头文件；定义只落在一个 .c；本文件私有的对象与函数 → 加 static。
   - 判停条件: 头文件同时被模块 A、B include 且 A、B 也要其私有组件时，拆分"公共头"与"内部头"。

4. **检查单一定义与遮蔽**
   - 完成标准: 全工程每个外部变量/函数恰有一个定义；include guard（或 #pragma once）齐全；无内层变量隐藏外部同名变量；`extern` 声明与定义类型一致。
   - 判停条件: 发现定义/声明分离后类型不一致 → 标记潜在 undefined behavior/链接时垃圾值，需回核对齐。

5. **🛑 STOP · 仅链接错误修复改动范围大时确认**
   - 完成标准: 检查结果无重复定义/未定义引用，直接给出验证步骤。
   - 判停条件: 仅当存在需跨多文件改动的重复定义/未定义引用（涉及多个 .c 的 extern 删除或改名）时暂停，列出受影响文件清单，由用户确认改动范围后再统一修改。

6. **验证链接**
   - 完成标准: 列出编译命令（各 .c 独立编译+链接），确认重复定义与未定义引用为 0；给出"改一处共享声明全工程生效"的验证步骤。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 所有代码仍在一个源文件（无需 extern/头文件组织，先做函数分解）；
- 用户问单个函数的原型/隐式声明问题（function-prototype）；
- C++ 的命名空间/内联变量/K&R 不适用（本 skill 为 C）。

### 作者在书中警告的失败模式

- 过度使用外部变量 → "数据关系模糊不清、值可能被意外修改、程序修改困难"（第1章 §1.10）；
- 违反"每个外部对象只能有一个定义" → 重复定义链接错误（第4章 §4.5）；
- 变量名隐藏外部同名变量 → "很可能引起混乱和错误"（第4章 §4.2）；
- 不把共享声明集中到头的做法 → 多处手工拷贝声明，改一处漏一处。

### 作者的盲点 / 时代局限

- 书中以 UNIX 多文件编译模型为背景；现代构建系统（Make/CMake）会约束 include 路径与依赖，头文件环路需依赖设计。
- C 模块化仍无命名空间（C23 之前），static + 约定式前缀是主要封装手段。

### 容易混淆的邻近方法论

- `function-decomposition`（函数级拆分 vs 文件级组织）；
- `function-prototype`（原型语法 vs 作用域/链接纪律）；
- `storage-class`/static 双重语义（本 skill 用文件级 static 链接限制，函数内 static 生存期是另一主题）。
