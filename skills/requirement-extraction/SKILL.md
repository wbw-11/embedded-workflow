# 需求提取与整理（脏输入 → 需求规格表）

## 适用场景

- 客户微信聊天记录（文字/截图）、语音通话转写、口头描述 → 整理成产品需求
- 旧产品说明书 / 历史项目文档 → 提炼新项目需求基线
- 零散邮件 / 会议纪要 / 招标要求 → 结构化需求
- 需求中途变更 → 增量追加，不覆盖已冻结需求
- 提供原理图 / 芯片手册 / 网表 → 从资料中提取可验证的接口约束并关联到需求

## 触发词（AI 看到即触发本技能）

聊天记录、微信截图、客户需求、需求整理、整理需求、产品说明/规格、需求文档/规格表、语音转写、通话录音、旧说明书、招标要求、会议纪要、邮件需求、项目需求。

## 前置边界（何时不适用）

- 纯技术咨询、通用问答 → 不需要
- 已有正式需求文档 → 不重复提取，直接进入评审
- 需求信息量不足以支撑 REQ 编号 → 先追问再整理，禁止凑数

## 执行流程

### 第一步：盘点输入并分类

| 输入类型 | 处理手段 | 产出中间物 |
|---|---|---|
| 微信聊天截图 | 本地 OCR 转文本；截图像素差时放大再识别 | 对话文本（带时间线） |
| 语音/通话录音 | 先转文字（用户提供转写稿或 ASR 工具），无转写稿时标注"待转写" | 转写文本 |
| 旧说明书/PDF | 提取文本（含扫描件 OCR） | 章节文本 |
| 口头描述/随手记录 | 直接整理，标注不完整处 | 要点清单 |
| 原理图/网表/芯片手册 | schematic-reading / datasheet-lookup 提取接口事实，**作为需求的硬约束证据** | 接口事实表 |

**规则：输入源必须标注**。每行需求必须能回溯到"哪条聊天记录 / 哪页说明书 / 哪段录音"。AI 不得编造来源。

### 第二步：识别语句意图（三分类）

对每一条原始素材，判定它属于哪类，**逐条贴标签**：

| 类别 | 标签 | 例子 | 处理 |
|---|---|---|---|
| 功能需求 | (Ф) | "要能远程开关" | 进需求表 |
| 非功能约束 | (N) | "响应要快"、"不能太贵"、"要过认证" | 进约束表（量化如可能） |
| 边界信息 | (B) | 芯片型号、供电、联网方式、量产数量 | 进"项目基本信息区"，供硬件评估用 |

判定不清的 → 标 (?) 进入"待澄清清单"，**不猜**。

### 第三步：需求编号与优先级

- 每行功能需求给 `REQ-xx` 编号（xx 从 01 顺序编号，不按严重度重排，保证变更追加不乱）
- 优先级：`P0` 无此功能产品不成立 / `P1` 必须有但可延后 / `P2` 锦上添花可砍
- 优先级**初步由 AI 依据证据强度拟定，用户复审确认**（AI 不改判用户已明确的口径）

### 第四步：补全四要素（每行 REQ 强制四列）

| 必需列 | 内容 | 示例 |
|---|---|---|
| 使用场景 | 谁 / 何时 / 何地 / 做什么 | 现场工人/设备上电后/产线/查看当前温度 |
| 交互规格 | 操作步数、反馈方式、失败提示 | 按键1次→LED闪2下=已开机；失败→蜂鸣2次 |
| 验收标准 | 可测量、可验证的指标 | 上电 3s 内出读数；-20~60℃ 误差 ±1℃ |
| 关联证据 | 来源标签（聊天/说明书/原理图引脚） | 微信 2026-09-05 23:41；原理图 U9 pin4 |

**非功能约束**（响应时间 / 功耗 / 认证 / 成本 / 存储寿命）单独成表，同样带证据。

### 第五步：冲突与缺漏清单（关键增值步骤）

在交付文档中专列两节，**不静默合并**：

1. **冲突表**：同一事项不同来源说法矛盾 → 逐条列出，标冲突来源，抛给用户裁决
   - 例：聊天记录说"锂电池供电"，旧说明书写"DC5V 适配器" → 冲突，需用户确认
2. **缺漏表**：需求明显要但素材里没有的项 → 列出并标"待确认"
   - 例：有"远程开关"但没说联网方式 → 缺"通信方式"

### 第六步：产出需求规格表

文档骨架（与四步准备①产出物同构，可直接剪贴）：

```
# 需求规格表 · <产品名>
## 0. 项目基本信息（芯片/供电/通信/量产/客户）       ← 来自边界信息
## 1. 需求表（REQ-xx | 优先级 | 功能 | 场景 | 交互规格 | 验收标准 | 证据）
## 2. 非功能约束表（响应/功耗/认证/成本/存储寿命 | 量化值 | 证据）
## 3. 冲突表（待用户裁决）
## 4. 缺漏表（待确认）
## 5. 待澄清清单（(? ) 项，含我的追问建议）
```

- 天然同时满足：`software-design-doc` 第 1 章需求追踪表、四步准备①需求规格表
- 交付格式：Markdown 草稿 → 用户确认后转 Word 正式版落 `Doc\`
- 归档命名：`需求规格_<产品名>_Vxx.md`，版本与项目版本同步

### 第七步：确认门槛（延续四步准备判定标准）

- 交付时**明确列出需要用户裁决的问题数**（冲突 N 条 + 缺漏 M 条 + 澄清 K 条）
- 用户对需求表给出肯定性确认（OK/确认/可以）后才允许流入下一步（架构设计）
- 模糊回答不放过，按"必问 8 项"思路继续追问

## 需求中途变更处理（变更回流闭环）

- 新消息 → 追加新 REQ 行，**禁止原地修改已冻结需求**
- **变更影响评估强制带出"回归用例清单"三栏表**：

| 受影响 REQ | 受影响模块 | 需回归测试用例（L0 单测 / L2 真机自检 / 验收标准） |
|---|---|---|
| 示例：REQ-03（改远程开关） | 联网模块 / 按键模块 | L0：状态机切换用例；L2：100 次开关循环；验收：≤1s 响应 |

  关联来源：software-design-doc 测试矩阵 / peripheral-test-template / Vn 验证计划，按 REQ 编号关联。
- 变更经用户确认 → 回归结果回填 `回归结果_<日期>.md` 并交 test-report 汇总
- 同字段多次变更 → 保留修订记录行（旧值→新值→变更原因→来源），不覆盖

## Pitfalls

- 禁止把 AI 的推断伪装成客户原话——需求行与来源一一对应，无来源行必须标 (?) 或进缺漏表
- 聊天记录口语裁剪时不改原意；"快了"这类模糊表述必须追问量化（"多快算快？"）
- 冲突/缺漏不静默合并——漏一个冲突到开发期代价是返工
- 语音转写稿错别字多，业务关键词（芯片/协议/引脚）需人复核
- 隐私线：客户聊天记录只在本项目内使用，不外传、不入通用知识库

## Verification

- 纯文本聊天（3-5 条记录）→ 生成需求表，验证：REQ 编号连续、四要素齐全、冲突/缺漏清单非空
- 聊天截图 → OCR 后同上，验证 OCR 错字对业务关键词的影响（人工复核一次）
- 旧说明书 → 验证提取章节与需求表的对应关系
- 需求变更追加 → 验证新 REQ 追加而非覆盖、影响评估存在
