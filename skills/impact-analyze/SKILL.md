# 代码变更影响分析

## 适用场景

- 用户修改了 .h 头文件，需要知道哪些 .c 文件受影响
- 用户改了函数签名（参数/返回值），需要定位所有调用点
- 重构前评估影响范围
- 用户问"改了这个头文件会影响什么"

## 脚本位置

`$env:USERPROFILE\Tools\impact-analyze.ps1`

## 使用方法

### 分析头文件变更影响

```powershell
# 分析 uart.h 在当前项目中的影响
impact-analyze -Header uart.h

# 指定项目路径
impact-analyze -Path "<项目目录>" -Header uart.h

# 同时分析头文件和特定符号
impact-analyze -Header uart.h -Symbol uart_init

# 显示详细结果（不截断）
impact-analyze -Header uart.h -Detail
```

### 仅分析符号引用

```powershell
# 查找 gpio_read 在项目中的所有使用位置
impact-analyze -Symbol gpio_read
```

## 输出解读

### 影响程度分类

| 级别 | 判断标准 | 含义 |
|------|----------|------|
| [高] | 调用该头文件中函数/宏 ≥5 次 | 必须同步修改 |
| [中] | 调用 1-4 次 | 可能需要修改 |
| [低] | 仅 #include 但未使用其中符号 | 仅需重新编译 |

## 项目类型自动识别

脚本自动识别：ESP-IDF（sdkconfig/idf_component_register）、Keil ARM（.uvprojx）、Keil C51（.uv2）、通用 C

## 与 AI 的协作流程

当用户修改了头文件或函数接口时：

1. **先运行影响分析**：
```powershell
cd <项目目录>
impact-analyze -Header <修改的文件名>
```

2. **解读结果并制定修改计划**：
   - 列出所有高影响文件，按优先级逐个修改
   - 对每个文件说明需要修改的具体内容

3. **执行修改**：
   - 先改高影响文件
   - 每改一个文件就编译验证

4. **编译后验证**：
   - 编译通过不代表功能正确
   - 高影响文件需要单独功能测试

## Pitfalls

- 分析基于静态文本搜索，不能检测函数指针间接调用
- 同名但不同命名空间的符号可能误匹配
- `#include <uart.h>`（尖括号）不会被检测到，只匹配 `#include "uart.h"`
- 大型项目分析可能较慢，建议先限定 `-Path` 缩小范围
- 修改宏定义时影响范围通常比函数更大，因为宏在预处理阶段展开

## Verification

- 影响分析后编译通过
- 高影响文件逐个功能验证
- `git diff` 确认所有受影响的调用点都已更新
