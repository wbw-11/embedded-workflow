# 未定义行为与求值顺序：识别并规避

## R — 原文 (Reading)

> "C语言没有指定同一运算符中多个操作数的计算顺序…因此，如果函数f或g改变了另一个函数所使用的变量，那么x的结果可能会依赖于这两个函数的计算顺序。为了保证特定的计算顺序，可以把中间结果保存在临时变量中。"（第2章 §2.12）
>
> "a[i] = i++; 的问题是：数组下标i是引用旧值还是引用新值？对这种情况编译器的解释可能不同，并因此产生不同的结果。C语言标准对大多数这类问题有意未作具体规定。"（第2章 §2.12）
>
> "同大多数语言一样，C语言没有指定函数各参数的求值顺序。因此，"printf("%d %d\n", ++n, power(2,n)); 是错误的，因为不知道n的自增运算在power调用之前还是之后执行。"（第2章 §2.12）
>
> — B. W. Kernighan & D. M. Ritchie, 第2章 §2.12

---

## I — 方法论骨架 (Interpretation)

C 的规范对**大量行为有意不做规定**，以换取各机器可选择最优执行路径。这带来两类不可移植的"坑"：

- **求值顺序未指定**：二元运算符两操作数与函数各实参的计算顺序不固定——`f()+g()` 谁先算、实参 `++n` 何时生效都不保证；
- **副作用时点未定义**：同一表达式中对同一变量多次自增/赋值（`a[i]=i++`、`i=i++`）结果不唯一，是"未定义行为"——编译器可做任何事，任何后果都合法；
- 辨析两个词：**未指定行为**（unspecified，合法但不保证顺序）vs **未定义行为**（undefined，完全不可依赖、可能崩溃/出错但不报错）。

应对方法是一套防御性纪律：**凡是结果依赖求值顺序或副作用时点的表达式，立即拆成多条明确次序的语句，中间量存入临时变量**——主动消除对编译器自由度的依赖。

## A1 — 书中的应用 (Past Application)

### 案例 1: printf 参数顺序陷阱
- **问题**: `printf("%d %d\n", ++n, power(2,n))` 在不同编译器可能输出不同结果。
- **方法论的使用**: 作者识别出函数实参求值顺序未定义，++n 与 power(2,n) 谁先算不确定。
- **结论**: 把语句拆开 + 用临时变量：`++n; printf("%d %d\n", n, power(2,n));`。
- **结果**: 改写后输出确定、可移植（第2章 §2.12）。

### 案例 2: 逆波兰计算器对减法顺序的处理
- **问题**: `push(pop() - pop())` 两个 pop 的求值顺序未定义，减法不满足交换律结果不确定。
- **方法论的使用**: 先弹到具名临时变量 op2，再 `push(op2 - pop())` 或显式保存两操作数。
- **结论**: "把中间结果保存在临时变量中" 是通用解法。
- **结果**: 计算器在任意编译器上结果一致（第4章 §4.3）。

### 案例 3: 未定义行为清单式的标注
- **问题**: 全书多处用"行为是未定义的"标注危险用法（越界、free 后用、printf 格式串异常）。
- **方法论的使用**: 作者给出的不是一张表而是一条评定原则——凡结果依赖机器/编译器自由裁量的写法都不可移植。
- **结论**: 好代码只依赖"语言保证成立"的部分。
- **结果**: 全书传递"主动规避"而非"侥幸可跑"的态度。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 同一段代码换个编译器/O3 优化开关结果就变，或运行结果随机闪变；
2. 同学/同事的代码里出现 `a[i]=i++`、`i=i++`、`x = f() + g()`、`printf(..., ++n, f(n))`，想确认是否安全；
3. 嵌入式固件在 debug/release 下行为不一致，怀疑是求值顺序/寄存器副作用问题；
4. 学习 C 标准时想区分"未定义行为/未指定行为/定义良好的行为"；
5. review 代码时按规范排查过不可移植表达式。

### 语言信号 (用户的话里出现这些就应激活)

- "为什么换编译器结果不一样？"
- "a[i]=i++ / i=i++ 是未定义的吗？"
- "f()+g() 谁先算 / 参数求值顺序？"
- "undefined behavior / unspecified / side effect / evaluation order"
- "这段代码为什么时对时错？"

### 与相邻 skill 的区分

- 与 `operator-precedence` 的区别: 它管"各级运算符谁优先"（静态优先级、可查表），本 skill 管"求值顺序与副作用时点"（动态、基本未定义）。
- 与 `memory-safety` 的区别: 越界/free 后用这类内存错误常是未定义行为的实例，但 memory-safety 聚焦资源纪律（该 free/不该用），本 skill 聚焦表达式与语言契约本身。

## E — 可执行步骤 (Execution)

1. **扫描范围内的显式副作用点**
   - 完成标准: 列出表达式里所有自增/自减/赋值/函数调用（可能有副作用的点），以及它们共享的变量集合。
   - 判停条件: 若同一变量在一个完整表达式内出现两次以上副作用，跳到步骤 3 确认未定义行为。

2. **🔴 CHECKPOINT · 仅行为分类歧义时确认**
   - 完成标准: 表达式可明确归为"未定义/未指定/良好"其中一类时，直接进入步骤 3，不打断用户。
   - 判停条件: 仅当表达式落在"未指定 vs 未定义"边界（如依赖某实现扩展、跨标的宏）无法立刻定类时，向用户复述分类依据与理由，确认后再继续。

3. **判定顺序是否被语言保证**
   - 完成标准: 套用保证规则（`&&`/`||`/`?:`/`,` 的求值与短路次序有保证；其余二元/实参/下标侧一般无保证），标注每个位置"未指定"还是"未定义"。
   - 判停条件: 只要出现"未定义"，给出的结论必须是"改写"，不能是"应该能跑"。

4. **🛑 STOP · 仅改写影响语义时确认**
   - 完成标准: 改写仅拆分表达式、语义等价时，直接给出多语句版本。
   - 判停条件: 仅当改写会改变原表达式的求值结果/副作用次数（如 `f()+g()` 先后顺序会对输出有影响、而用户依赖其中一种顺序）时暂停，明确告知"改写后求值顺序固定为 X，原代码顺序未定义"，由用户确认可接受后再给出改写版。

5. **改写并把中间值钉进具名变量**
   - 完成标准: 输出改写后的多语句版本，每步只含语言保证的求值行为；注明哪些中间量来自临时变量。
   - 判停条件: 若改不开（表达式嵌入宏参数重复求值），转交 macro-vs-function 检查是否宏本身有缺陷。

6. **给结论**
   - 完成标准: 明确告知原写法"未定义/未指定/良好"，并给出可移植版本与理由。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是查运算符优先级（见 operator-precedence 能力卡）；
- 用户问的是 C11/C17 引入的新时序/泛型语义（本书按 K&R/ANSI 契约，未覆盖）；
- 用户在调试性能而不是正确性。

### 作者在书中警告的失败模式

- 依赖副作用顺序想在单条表达式里"一次做完多个操作"（第2章 §2.12）；
- 位测试表达式漏括号 `x & MASK == 0`（那是优先级问题，但同段作者已强调下界关系）；
- `max(i++, j++)` 宏参数重复求值（第4章 §4.11.2，见 macro-vs-function）。

### 作者的盲点 / 时代局限

- 书中用"错误/危险"标注而非系统命名得很细；现代标准把未定义行为细分为 unspecified/undefined/implementation-defined 且工具（UBSan、静态分析）可辅助检测，本书时代无此工具。
- 现代可参考编译器警告（`-Wsequence-point`）自动发现，书中靠人工。

### 容易混淆的邻近方法论

- "参数默认提升"（type-conversion）——那是类型层面的自动但**确定**的转换，与求值顺序无关；
- "宏的重复求值"（macro-vs-function）——副作用在宏里放大，但根因与本 skill 不同（文本替换 vs 语言契约）。
