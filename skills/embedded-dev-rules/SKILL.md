## 开发红线（绝对不可违反）

> ⚠️ **本节为嵌入式开发红线的唯一权威来源**。user_profile.md 和工作流程手册中的红线规则均引用此处，不再重复定义。

1. **禁止用 PowerShell/XML 工具修改 Keil 工程文件**（.uvprojx/.uvoptx），会损坏 XML 结构导致 Cannot read project file
2. **不凭记忆写寄存器配置** — 必须先执行 datasheet-lookup 技能的验证流程（项目头文件 → Keil 系统头文件 → PDF → 官方网页）
3. **不凭记忆写库函数名** — 调用厂商库函数前，必须 grep 搜索头文件确认函数名和参数
4. **不擅自修改核心通信机制** — 修改已有项目时：
   - 原始代码能工作 → 保持核心机制（DMA/中断/轮询）不变，只做规范优化
   - 原始代码有问题 → 先定位根因再针对性修改，不能按自己偏好重构
   - 重构架构必须上下层配套完整修改，不能只改一半
5. **功能优先于规范** — 代码审查清单（详见 embedded-code-review 技能）是优化建议不是强制要求，先保证功能正常再逐步优化
6. **ISR 位置必须与参考项目保持一致**，不凭经验自行调整（详见 embedded-code-review 中断安全章节）
7. **操作外部目录前必须先检查 sandbox.json 读写权限** — 修改 Tools 脚本、Skill 文件、memory 文件等外部目录前，确认 sandbox 配置允许写入
8. **禁止头文件中定义全局变量** — 头文件只声明 `extern`，定义放 `.c` 文件（防止多文件包含时重复定义）
9. **禁止使用未初始化的局部变量** — 所有局部变量必须显式初始化（`= 0U` / `= {0}`），嵌入式栈上未初始化值是真正的随机垃圾

## 修改代码强制检查

> ⚠️ **本节为修改代码检查规则的唯一权威来源**。user_profile.md 和工作流程手册中的相关内容均引用此处。

- 修改 .c 文件后 **必须检查相关 .h**：函数签名、宏定义、结构体、extern 声明是否需同步
- 修改 .h 文件后 **必须检查所有 include 它的 .c**：确认引用处是否受影响（可用 impact-analyze 技能）
- 检查清单：函数声明与实现签名一致、宏值变更后使用处兼容、结构体增删字段后初始化代码更新、条件编译路径正确、extern 声明与定义类型一致
- **不允许只改 .c 不看 .h，或只改 .h 不看 .c**

## 修改代码工作流程

### 1. 修改前备份

修改已有文件前先复制 `.bak` 备份。如果项目用了 git 且 status 干净，可跳过。

### 2. 引脚冲突检测

写驱动前用 pin-check 技能检查引脚可用性。发现多外设共用同一引脚时立即告知用户。

### 3. 初始化顺序

main.c 中初始化必须按此顺序：系统时钟 → GPIO 基础配置 → 外设驱动（UART → SPI → I2C → ADC）→ 中断使能（EA = 1 放最后）。不允许在外设初始化前使能中断。

### 4. 编译验证

写完代码后自动编译验证：Keil 项目用 keil-auto-flash 技能，ESP32 项目用 esp-idf-build 技能。编译失败先修复再交给用户。工具链不可用时明确告知"未能编译验证，请自行确认"。

### 4.5 烧录前自动审查门禁（全局强制，2026-09-03 起对所有项目/所有芯片生效）

> 适用范围：**任何项目、任何芯片**（含未用过的芯片、未来的新项目）。不是某个项目的专属流程。
> 教训：V8.2f 曾未过门禁直接烧录，审查时才发现 CSRF 漏洞已存在于已上板固件（Cookie 缺 SameSite=Strict）。

编译通过后、交给用户烧录前，**必须按序执行以下三件套，缺一不可**：

| 步骤 | 内容 | 工具/依据 |
|---|---|---|
| ① 静态门禁 | 跑 code-style-check.ps1 -Checks overflow,defensive（全局脚本，跨芯片通用），非 0 先处理再继续 | USERPROFILE\Tools\code-style-check.ps1 |
| ② 人工快查三项 | 针对**本次改动**：安全（HTTP/Cookie/越权/CSRF，Cookie 必须 SameSite=Strict）/ 并发（跨任务变量 volatile、锁）/ 缓冲区（定长+边界+禁 strcpy/sprintf） | 参考 esp-idf-build 技能 2.5.0 表格 |
| ③ 产物新鲜度 | 产物（hex/axf/bin）时间戳必须比所有源码（.c/.h）新，防烧旧固件；**版本号三处一致**（printf `FW Vxx` = 产物文件名 = 日志首行，规范 §四③） | 各编译技能时间戳检查节 + dev-flow 版本门禁（-SkipVersionGate 豁免） |

- 新芯片/新项目首次烧录：除三件套外，附加 chip-rules（该系列规则）+ datasheet-lookup（寄存器坑）核对。
- 未用过的芯片：静态门禁（C 通用规则）与人工三项均不依赖芯片型号，直接适用；芯片特有坑由 chip-rules/datasheet-lookup 补充。
- 各烧录入口技能（esp-idf-build / keil-auto-flash / stcgal 等）均执行本门禁；用户自备工具的链路由用户确认后同样先过三件套。

### 4.6 驱动验证四层标准（全局强制，2026-09-03 起对所有项目/所有芯片生效）

> 适用范围：**任何项目、任何芯片**。回答"驱动写对了没"必须按四层闭环验证；单靠"官方例程基线对照"不足——它只证明硬件通路与 happy path（官方接口能跑），不测你的 API 契约、边界、错误路径、性能、并发。
> 四层角色：**L0 日常回归主力（最便宜，秒级）→ L2 验收硬条件（扛得住）**；L1/L3 为两道门槛，保留不可跳。

> **驱动开写判据（先做需求分析再写码，任何驱动开发强制）**：写驱动第一行代码前，必须完成三件套，缺一不可——
> ① **接口契约**：暴露哪些 API / 参数结构体，同步 or 异步 / 阻塞 or 非阻塞，错误处理策略（超时 / 错误码 / 重试），ISR 边界（中断里干什么）——唯一需要人拍板的部分，先定为敬。
> ② **硬件证据链**：寄存器名与位定义（datasheet-lookup 查证顺序），引脚分配与冲突检查（pin-check），时钟 / 波特率 / 时序参数——被硬件钉死，只查证不讨论。
> ③ **验证标准**：官方例程基线对照、自检方式（回环 / 引脚检测）、单元测试 mock 方案、性能预算——“怎么算写对了”。
> 三件套就绪并经用户确认后，才允许写驱动代码；后续验证执行仍按下表 L0–L3 四层标准。

| 层 | 名称 | 验证什么 | 工具/依据 | 时机 |
|---|---|---|---|---|
| L0 | 单元测试（主机端） | 参数校验 / 边界 / 错误码 / 状态机，mock HAL，不依赖硬件 | embedded-unit-test（Unity + CMock） | 每次改完驱动即跑；挂 pre-commit 门禁 |
| L1 | 官方例程基线对照 | 硬件通路 / 库配置序列（happy path） | 官方例程 + 官方库 | 硬件变动或怀疑硬件时的一票否决器 |
| L2 | 真机自检 + 压力 | 满负荷回环 / 错误注入 / 长跑 / 性能时序 | peripheral-test-template | 每版 Vn 交付前必跑 |
| L3 | 集成 + 脱机验证 | 多外设并发 / 拔调试器独立上电再验 | 既有 Vn 脱机红线 | 每级 Vn 通过后 |

强制规则：
1. **L0 写驱动器必建**：逐驱动建单测（改 .c/.h 时同步补），P0 失败阻止提交——与 code-style-check 并列挂进 pre-commit 门禁，把逻辑错误挡在真机之前。
2. **L2 pass 标准必须量化**：禁止"测一下收发正常"；写成如"115200 满速连续收发 1MB 零丢包 + 错误注入 N 次全部恢复 + 长跑 48h 无复位"，量化了才有资格进验收、留回归基线。
3. **L1 定位**：是"怀疑硬件或库被改坏"时的一票否决器，不是常规验收手段；happy path 通过 ≠ 驱动正确。
4. **结果闭环**：L0/L2 结果经 test-report 汇总入缺陷台账；回归基线只增不减，每版必跑，防旧 bug 复活。

### 4.7 存储寿命设计清单（全局强制，2026-09-04 起对所有项目/所有芯片生效）

> 适用范围：**任何项目、任何芯片**。写参数存储代码（NVS / DataFlash / 外部 EEPROM / SPI Flash 掉电保存）时，写第一行代码前必须过寿命账，禁止默认直接写固定扇区。
> 教训：voice_motor 音量滑块曾因缺防抖高频写 NVS；开发期全片擦除烧录频繁但无害，真正杀手是固件运行时高频写同一扇区。

**写存储前必算的寿命账**（写第一行代码前完成并告知用户）：

1. 查 P/E 寿命（L3 项目记忆/数据手册；常见参考：MCU 内置 NOR≈1 万次，STC8 DataFlash≈10 万次，外部 SPI NOR≈10 万次，I2C EEPROM≈100 万次）
2. 估算日写次数（写频率 × 运行时占比）→ 寿命天数 = P/E 寿命 ÷ 日写次数
3. 判定：预计寿命 < 5 年 或 全生命周期写入 > 寿命 10% → **必须上缓解手段**
4. 缓解手段（按需组合）：
   - 读回比较：值未变化不写（幂等，embedded-code-review Q10 已有）
   - 防抖/合并写入：高频滑块/计数先 RAM 累计，超阈值/超时再落盘
   - 环形写入/扇区轮换：多扇区轮写 + 序号/魔数识别最新块
   - 影子副本：写完校验 + 双备份，防写一半掉电
   - 高频数据迁移：外置 I2C EEPROM（寿命更高）或 RAM（允许掉电丢失）
5. **审查对照**：embedded-code-review「长运行-Flash 磨损均衡」必须命中；dev-flow 主循环自动检测存储写 API 并提示本清单
6. 写入设计评估，亮出免检条件：写频率极低（如配网凭据一年几次）可不做磨损均衡，但读回比较仍建议保留

### 4.8 栈管理规范（全局强制，2026-09-06 起对所有项目/所有芯片生效）

> 适用范围：**任何项目、任何芯片**（RTOS 任务栈 / 裸机调用栈）。新增"吃栈"代码（渲染、协议栈、库、递归、大局部数组、无 FPU 浮点格式化）时，必须先核对栈余量，禁止"能编译能跑"就当通过。
> 教训：GD32F407VE Zephyr LVGL 项目，LVGL 渲染线程栈默认 4096，渲染整屏壁纸栈溢出 → **全黑但固件正常活着**（无故障寄存器、串口 alive 正常），排查数小时。此前 LZ4 壁纸解码失败被跳过反而 UI 正常，造成"壁纸格式是原因"假象。修复=栈 4096→16384。

**栈规格红线**：
1. 渲染/深调用线程栈 **16KB 起步**（LVGL 渲染、协议栈、加解密、递归算法），其他线程按调用链估算，留 ≥30% 余量
2. 开启栈保护让溢出"可见"而非静默：MPU_STACK_GUARD / HW_STACK_PROTECTION / FreeRTOS configCHECK_FOR_STACK_OVERFLOW=2 / ESP-IDF CONFIG_COMPILER_STACK_CHECK

**开发期必做（改动后）**：
1. 用 RTOS 栈检测工具核对峰值余量，记入改动总结：Zephyr 开 CONFIG_THREAD_ANALYZER 用 thread_analyzer_print_all()；FreeRTOS/ESP-IDF 用 uxTaskGetStackHighWaterMark()；裸机（STC8 等）控制调用深度、大局部数组移静态区
2. **症状识别**：栈溢出是"伪装大师"——黑屏、随机复位、看门狗、HardFault、数据错乱、偶发正常，都可能只是栈小。遇"全黑/死机但固件活着"先查栈，勿先怀疑业务逻辑

### 5. 警告处理

编译后必须检查警告，用 log-analysis（Skill）+ warning-db（Tools 脚本，RunCommand 调用）匹配已知警告。所有警告处理完毕后再交给用户。

## 新项目启动流程（四步准备流程）

> ⚠️ **本节为新项目启动的唯一权威来源**（v2.3 替代原 8 项清单，8 项降为第一步摘要）。user_profile.md 和工作流程手册中的相关内容均引用此处。
>
> 2026-08-11 数码管项目教训：跳过此流程会导致反复踩坑、项目推倒重来，强制执行。

用户说"开始新项目"、"新建工程"、"移植到新芯片"时，**必须完成以下四步准备流程，以书面文档形式产出，经用户逐项核对确认"OK"后才允许写第一行代码**。禁止凭推测直接写代码。

### 第一步：需求分析与规格定义（明确目标）

**需求来源前置检查（v2.6.1 新增）**：若需求来源是**散乱材料**（客户微信聊天/截图/语音转写/旧说明书/口头描述），进入四步准备**之前**先调 `requirement-extraction` 技能（脏输入 → 需求规格表，含 REQ 编号 + P0/P1/P2 + 四要素 + 逐行证据 + 冲突/缺漏表），产出经用户确认后才进入本步细化；若已有正式需求文档则直接进入。

将模糊想法转化为具体的工程指标：
- 功能需求细化：拆解为独立功能模块，对显示类项目需明确"每一位显示什么字符、小数点位置、从左到右顺序"等细节
- 非功能性指标：实时性（如扫描频率≥50Hz）、功耗限制、存储容量上限
- 约束条件确认：硬件平台限制、行业标准、开发周期

**信息收集摘要（原 8 项）**：①芯片型号 ②开发方式 ③晶振频率和时钟源 ④目标外设 ⑤硬件原理图 ⑥官方例程 ⑦数据手册 ⑧下载工具

### 类似项目方案调研（v2.6.2 新增，需求明确后、进入第二步前自动执行）

需求规格表确认后，**先搜类似项目再动手**，避免重复造轮子、踩别人已踩过的坑：

1. **搜索源与关键词（GitHub + Gitee 并联，gh CLI 优先）**：
   - GitHub：**优先用 gh CLI**（`gh search repos` / `gh search code`，2026-09-15 实测可用，账户 your-github-username）；mcp_GitHub `search_repositories` 若凭据有效亦可。
   - Gitee：用当前会话可用搜索能力（mcp_gitee `search_open_source_repositories`）。
   - 关键词组合：`芯片型号` + `功能词`（如 `STM32F407 温控` / `esp32 sensor wifi`），中英文各查一轮；再补一次代码级搜索（gh search code / search_code）精确匹配关键模块（如协议帧定义、传感器型号）。
2. **产出「类似项目速查表」**（写入 Doc\，供②硬件评估/③架构参考）：

   | 仓库/项目 | 芯片/平台 | 覆盖功能 | 许可证 | 可复用度 | 参考价值 |
   |---|---|---|---|---|---|
   | 名称+star | 主控 | 与本项目重合项 | MIT/GPL/无 | 高/中/低（代码能直接搬/只能看思路/仅线索） | 引脚方案/算法/协议/踩坑 |

   速查表逐行填，能复用的部分标注"可参考 xxx 仓库的哪部分"。
3. **开发建议（搜索后必给，交给用户裁决）**：①候选项目是否有成熟可复用方案 → ②可参考的部分（引脚分配/协议栈/算法/校准方式）→ ③建议自研的原因（许可证冲突/芯片不匹配/代码质量差/功能覆盖不足）。**复用第三方代码前必须过 license 检查**（反向工程注意）与 embedded-code-review 代码审查。
4. **边际控制**：搜索时间在 10-15 分钟内收尾；找到 2-3 个高价值项目即可深入，不宜无限搜。找不到高价值项目时如实说明"无直接可复用方案"，不硬凑。
5. **源故障降级（v2.6.5 新增 / gh CLI v2.6.6）**：GitHub（mcp_GitHub 或 gh CLI）返回认证失败/不可用、或 Gitee 不可用时，**不中断流程**——降级为可用源独跑，速查表标注"某源未生效（原因）"；完成后提示用户检查对应凭据（gh CLI 可 `gh auth login` 登录，授权后重启会话加载）。禁止因一个源故障卡住整个方案调研。

### 第二步：硬件平台评估与熟悉（摸清底子）

嵌入式软件与硬件强绑定，必须 100% 确认后才能写代码：

- **研读芯片手册**：MCU 内部架构、寄存器、时钟系统、中断控制器、外设接口
- **MCU↔外设连接表（强制表格 + 证据链）**：禁止用自然语言描述引脚，必须按以下模板输出，每一行必须有证据来源（网表文件行号 / PDF 页码 / 原理图截图编号），禁止凭经验猜引脚：

  | 信号名 | MCU引脚 | 外设芯片/引脚 | 方向(MCU→X) | 证据来源 |
  |--------|---------|---------------|-------------|----------|
  | （示例）NIX_DI | PD0 | 74HC595 U1 pin14 (DS) | 输出 | 扩展板 tel L98 + 核心板 tel L133 |

- **时钟源独立验证 + 宏配置模板（强制写死）**：默认优先使用内部 RC 振荡器（GD32: IRC16M / STM32: HSI / STC8: 内部IRC），**禁止默认使用外部晶振（HXTAL/HSE）**，除非用户明确提供晶振参数并书面确认硬件起振电路正常。必须在文档中写死以下信息，并在 V0 烧录前手工核对 system_xxx.c 中宏的注释状态：

  ```
  时钟源确认：
    系统时钟宏：__SYSTEM_CLOCK_168M_PLL_IRC16M  （示例，根据实际填写）
    SYSCLK 频率：168MHz（内部 16M RC → PLL 倍频）
    外部晶振：不使用 / 使用（频率____MHz，用户已确认起振）
    文件位置：Firmware/CMSIS/GD/GD32F4xx/Source/system_gd32f4xx.c 第 44-52 行
  ```

- **外部晶振起振确认方法（视觉检查 + 万用表测量，2026-08-20 新增）**：如果用户决定使用外部晶振，必须按以下顺序确认起振电路正常：
  1. **视觉检查**（用户做）：晶振是否存在 + 焊接是否正常 + 负载电容（22pF 左右）是否存在 + 频率丝印（如 "8.000"）
  2. **万用表测量**（用户做）：晶振两脚 vs GND，期待值约 VDD/2（1.65V），两脚压差接近 0V → 起振；一脚 0V 一脚 3.3V → 没起振
  3. **书面确认**：用户在四步准备文档里填"外部晶振：使用（频率 8MHz，起振✅）"
  - 备选方案：示波器测晶振脚正弦波（最准确，但探头电容可能影响起振，用 10x 档位）
  - 软件测试方案：IRC 启动后切换 HXTAL 看标志位（需要先验证 IRC 路径）
- **关键器件型号与极性提取**：如数码管型号、驱动芯片级联顺序、发送顺序、共阳/共阴极性、LED 点亮电平等
- **硬件原型验证**：条件允许时先验证硬件基本功能

### 第三步：软件架构设计与规划（搭好骨架）

- **确定系统框架**：裸机前后台 / RTOS（FreeRTOS 等）
- **分层架构设计**：HAL 层 → 驱动层 → 应用层，明确每层接口
- **接口与协议设计**：标准化 API 接口，通信协议帧格式
- **验证梯度设计**：设计 V0→V1→V2→V3... 多级验证步骤，确认代码真正运行后再推进。禁止直接写最终功能代码
  - **V0（代码可执行性铁律验证，分级兜底）**：必须是"代码运行到 main() 的最简验证"，按以下优先级选择：
    - **V0-A（优先）**：板载用户 LED，配置为推挽输出、周期性翻转闪烁（如每 500ms）→ 用户肉眼观察
    - **V0-B（兜底 A）**：无 LED 时，初始化 UART0/默认串口，循环输出固定字符串 → 用户串口助手确认
    - **V0-C（终极兜底）**：无 LED 也无串口，选 GPIO 排针引脚周期性翻转 → 用户万用表/示波器测电压跳变
  - **V0 未通过前，禁止写任何外设驱动代码**

### 第四步：开发环境与工具链搭建（准备武器）

- 软件工具链：IDE、交叉编译器、构建工具（Keil/ESP-IDF/Makefile/CMake）
- 硬件调试设备：调试器（CMSIS-DAP/ST-Link/J-Link）、逻辑分析仪、万用表、示波器
- 工程规范准备：版本控制（Git）、代码注释规范、测试框架

### 工具链搭建 SOP（第四步实操细化，通用不绑定具体机器）

> 第四步的概念要素（软件/硬件/规范）见上。本节为可执行的通用操作清单，所有路径/版本使用占位符，不绑定本机环境。路径检测一律动态化（环境变量 → 注册表 → 候选列表 → 全盘搜索兜底），禁止硬编码绝对路径。

**判定标准**：V0 骨架能编译通过并烧录成功，才算工具链搭建完成。

1. **确认芯片实际型号**：用 hardware-detection 技能读 Device ID，与声明型号比对，不一致即停并告知用户
2. **按系列选工具链**：查 chip-rules 对应系列规则（编译器、构建命令、产物格式、归档后缀）
3. **安装/确认芯片支持包（DFP）**：版本以厂商官网当前为准，IDE 内可选对应厂商 Pack
4. **生成工程骨架**：用 project-init 技能（main.c + 构建配置，按芯片系列模板）
5. **建立/切换板级配置**：用 board-config 技能（芯片型号、Flash/PSRAM、保留引脚、默认串口、调试器）
6. **构建验证**：优先命令行全量重建（禁止增量）；失败先修复再继续
7. **烧录验证**：确认调试器连接、芯片类型匹配后烧录
8. **V0 启动验证**：串口看到符合 `debug-log-standard` 格式的版本日志
9. **基线快照**：V0 通过后 git commit 或复制 `.baseline_v0_pass`，再写外设驱动

> 工具链不可用时**明确告知**"未能编译验证，请自行确认"，禁止假装编译过。
> 本步自动触发：hardware-detection → project-init → board-config。

### 执行门槛：用户确认判定标准

四步准备文档输出后，必须等用户**用明确肯定性文字确认**，才允许写任何代码：
- ✅ 算确认：OK、没问题、确认、可以、对、就这样、开始吧、写吧、过
- ❌ 不算确认：只回答了部分问题、模糊语气（"行吧""也行"）、只发表情、反问、指出文档有问题但没说整体OK

> 规则核心：**宁可多问一句，不要自认为用户默认同意**。

### V0 通过后的基线快照规则

V0 验证通过后，必须先做"基线快照"再写后续驱动代码：
- **有 Git 工程**：`git add -A && git commit -m "feat(v0): baseline passed"`，记录 commit ID
- **无 Git 工程**：手动复制整个工程目录为 `.baseline_v0_pass` 备份
- 后续任何一步出现"编译不过""烧录后没反应""V0 原本能跑现在也不行了"，立即与基线对比定位

### 文档存放位置约定

- 四步准备文档默认直接输出在聊天窗口供用户核对，不主动创建额外 .md 文件
- 仅当用户明确要求"存下来"时才在项目目录下创建文档文件
- 永久性跨项目规则写入 user_profile.md；项目级踩坑记录/引脚表写入 project_memory.md

> **流程钩子（v2.4 新增）**：走到以下节点自动调用对应技能，无需用户点名：

## 调试纪律强化（2026-09-01 ESP32 喇叭长线排查沉淀）

> 背景：一次"喇叭无声"排查横跨 10+ 轮烧录测试才定位，根因其实很表面（音源 PCM 全零）。复盘沉淀 5 条纪律，任何外设"输出无声/无效"类问题适用。

1. **数据源校验永远第一**：任何"信号打不出来"的排查，**第一步先验证"预期数据/波形源"本身是否为有效值**（如播放前打印 PCM `max|x|`、串口先发固定 0x55、PWM 先写死 100%）。数据源是 0 → 后面所有硬件/寄存器排查全是白费。**禁止先怀疑外设/链路/寄存器，最后才查数据源。**
2. **软件读数 ≠ 真相，两次无进展强制升级物理测量**：`gpio_get_level`、内部回环幅值、计数/过零率等"软件读数"可能是假象（实测 gpio_get_level 读 0，万用表 3.3V；mic 检到 880Hz 是板内电耦合假信号）。**连续 2 轮基于软件读数的假设无进展 → 必须升级**：万用表测引脚电平、示波器看波形、人耳听声、串口打印上游数据。物理证据优先级 > 软件读数。
3. **写寄存器前必查数据手册**：资料夹有手册就先解析手册确认寄存器位义与复位默认值（REG44 出厂默认 0x58 含回环位，手册一查即明）。**禁止只看组件源码/例程就推寄存器语义。**
4. **硬件资料先验实物一致性**：原理图/网络表/复用表在开工或疑点出现时，必须与"实际板"交叉核对（实物照片/万用表/用户确认）。旧版本资料与实物不符时，以实物为准并立即作废旧资料。
5. **memory 旧结论遇矛盾先存疑**：实测与历史结论（"XX 引脚低电平使能"）冲突时，**先复核旧结论是否过时/适用当前板**，再决定听谁的。硬件改版后 legacy 结论可能作废。

用户反馈"不行，现象是 xxx"后，必须执行以下闭环：

1. **记录**：写入 project_memory.md 的"踩坑记录"章节：

```
### [日期] [模块名] [错误现象]
- 现象：xxx
- 原因：xxx
- 解决方案：xxx
- 预防措施：xxx
```

2. **重建索引**：记录后必须执行 `knowledge-index -Index`，否则记录了但搜不到

3. **搜索前置**：下次遇到类似问题时，**必须先用 `knowledge-index -Search` 搜索历史踩坑记录**，避免重复犯错。不从头分析，先查有没有现成解决方案。

4. **重大踩坑后链路体检（v2.5.1 新增，触发：同一问题连续 ≥3 轮未解决后定位成功）**：定位完成 ≠ 流程闭环，按序执行四项体检，防止"旧结论污染/沉淀不生效"：
   - ① **memory 旧结论作废检查**：搜索 project_memory/user_profile 中与本次结论冲突的历史条目（关键词），逐条标注 ⚠️已作废/已证伪 + 指向新结论（2026-09-01 喇叭案例：遗留"NS4150 低电平使能"、"TC1508A 驱动喇叭"两条毒结论险些害下次重走弯路）
   - ② **规则落点分级核对**：新认知按"换芯片成立？"分级入 L1(embedded-dev-rules)/L2(chip-rules)/L3(project_memory)，禁止塞错层级
   - ③ **执行入口核对**：新纪律写了正文 ≠ SOP/门禁里有入口 —— 确认排查/开发 SOP 对应步骤已插入（如"数据源校验"必须出现在排查 SOP 第 0 步，而非只在理论章节）
   - ④ **knowledge-index -Index 重建**：改过任何 project_memory 后必须重建，并验证扫描路径覆盖完整（默认应含 $env:USERPROFILE\.trae-cn\memory\projects，路径失效会导致索引空转）

## 人机互动开发规范

> ⚠️ **本节为人机协作规范的唯一权威来源**（v2.3 新增）。目标：把嵌入式软件开发从「AI 黑盒写代码→用户被动验证」转变为「每个阶段用户都清楚进展、知道该做什么、有疑问立刻有交互」的透明协作流程。

### 规则 1：每轮回复必带「三栏进度看板」

项目未完成期间，任何回复**开头先放进度看板**，让用户一眼看清状态：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
项目进度看板（[项目名]）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
已完成：
  1. XXX
  2. YYY

当前阶段：
  [当前正在推进的步骤]

请你做的事（按顺序，必须具体可执行，禁止写"看一下"这种模糊指令）：
  1. [动作1，如：Keil按F8烧录]
  2. [动作2，如：按开发板RESET键]
  3. [动作3，如：观察PD8蓝色LED，看是否每秒闪烁一次]
  4. [动作4，如：把实际看到的现象回复我]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 规则 2：阶段切换必提醒 + 遗漏项自检

进入新阶段（四步文档→V0编码→V0烧录→V0验证→基线快照→V1→…→完成）时：
- 第一句明确告知阶段切换
- **自动做一遍前置遗漏项自检**，有缺失先暂停补漏，不硬推进

自检清单（固定项目，每次自动核对）：
1. 引脚表是否按强制表格输出 + 每行有证据来源
2. 时钟源宏是否写死具体宏名 + 文件位置 + 是否已核对注释状态
3. V0 验证方式是否选好（V0-A/B/C 三级兜底之一）
4. 用户是否对四步文档给出明确 OK

### 规则 3：代码+编译通过后，必等「用户烧录+观察+回报」

每写完一级验证代码（V0/V1/V2/...）并编译通过，**不自行推进到下一步**，直接停在「待用户操作」，输出标准操作清单等用户回报现象。

### 规则 4：硬件观察类结果，模糊回答必追问澄清

用户回复「没反应/不正常/乱码/不行」这类模糊描述时，**禁止自己猜原因**，必须先追问细节，给出结构化追问清单（如：是完全没动静还是有输出但不对？电源灯亮不亮？按 RESET 前后现象有无变化？烧录日志最后一行是什么？）。

### 规则 5：信息不确定 → 直接抛选择题，绝不「我觉得」

遇到分支点、信息矛盾、或用户没指定的方案选择时，**禁止自行决定**，必须给出结构化选项让用户选（推荐选项放第一个并标注）。

### 规则 6：出错/卡住时 → 透明化披露排查思路和优先级

任何失败/异常，第一时间告知问题描述 + 按可能性排序的排查方向，不悄悄绕过去。

### 规则 7：决策边界三问法

每个动作前先过一遍「行动前三问」自检：

| 自检问题 | 答"是"的处理方式 |
|---------|-----------------|
| ① 这一步是否需要用户硬件操作配合？（烧录、按RESET、换线、测电压） | 是 → 放入「请你做的事」看板，等用户回报 |
| ② 这一步是否需要用户感官观察硬件现象？（LED/数码管/串口/电机） | 是 → 放入「请你做的事」看板，给出观测点和示例回答 |

## MCP 工具使用规则

> ⚠️ MCP 工具与内置工具重叠时，**优先使用内置工具**（受 sandbox 约束，行为一致）。

| MCP 服务器 | 规则 |
|-----------|------|
| `mcp_Filesystem` | **禁用**（已停用）。read_file/write_file/edit_file/list_directory/search_files 全部用内置 Read/Write/Edit/LS/Grep/Glob 替代 |
| `mcp_pdf-reader-mcp` | **保留（快速文本提取）**。查 datasheet 寄存器/函数名时用 read_pdf（轻量优先）；复杂操作（合并/拆分/填表单/OCR）用 `pdf` Skill |
| `mcp_Fetch` | **禁用**。用内置 WebFetch 替代 |
| `mcp_GitHub`（独立版） | **停用**（与 GitHub 插件 `mcp_plugin_GitHub_github` 重复）。GitHub 操作统一走 GitHub 插件 connector |
| `mcp_gitee` | 按需使用。同 GitHub |
| `mcp_context7` | **优先使用**。查 ESP-IDF/FreeRTOS/库 API 时优先用 resolve-library-id + query-docs，不用 WebSearch |
| `mcp_Sequential_Thinking` | 按需使用。复杂推理场景 |
